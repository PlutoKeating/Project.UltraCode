基于对 **UltraCode (`v1.1.0`)** 官网（[ultracode.plutokeating.beer](https://ultracode.plutokeating.beer)）、[GitHub 源码](https://github.com/PlutoKeating/Project.UltraCode) 以及 **OpenCode V2（`v2.0`–`v2.4.1`）** 官方架构的逐文件核查，先给出核心结论：**UltraCode 并不是 OpenCode 的魔改分支或独立运行时，而是一个非侵入式的“插件 + 角色编排 + CLI 包装层”**。

它在**工作流工程化**（特别是你的 toC 前端视觉验收和跨会话接力）上对原生 OpenCode 做了非常精准的补强，但对 Claude Code 最底层的**上下文压缩与模型权重级对齐**并没有（也无法在插件层）做到 1:1 复刻。

---

### 一、 相对于原版 OpenCode V2，UltraCode 带来了哪些实质性亮点？

官方 [OpenCode V2](https://anoma.ly/notes/opencode-2-0/)（2026 年 10 月发布 2.0，11 月迭代至 [v2.4.1](https://github.com/anomalyco/opencode/releases)）本身已经补齐了集中式后台服务、Code Mode、异步子代理（`<background-result>`）、原生 `/goal` 以及后台压缩（`compaction.background`）。在此之上，UltraCode 在源码中实打实地增加了以下四项能力：

1. **权限硬隔离的“2+5”角色矩阵（而非单纯的 Prompt 扮演）**
UltraCode 在 [`packages/config/opencode/agents/`](https://github.com/PlutoKeating/Project.UltraCode/tree/main/packages/config/opencode/agents) 中定义了 `UltraBuild`（[`orchestrator.md`](https://github.com/PlutoKeating/Project.UltraCode/blob/main/packages/config/opencode/agents/orchestrator.md)）、`UltraPlan`（[`planner.md`](https://github.com/PlutoKeating/Project.UltraCode/blob/main/packages/config/opencode/agents/planner.md)）和 5 个后台专家子代理。关键在于它用 OpenCode 的 `permissions` 做了**物理权限隔离**：
* `UltraPlan` 禁止修改任何业务代码（`edit: "*" -> deny`），只允许写 `.opencode/plans/**`，且强制为每个 Sprint 产出带验收命令和 UI 标准的 **Sprint Contract**。
* `visual-evaluator`（[`visual-evaluator.md`](https://github.com/PlutoKeating/Project.UltraCode/blob/main/packages/config/opencode/agents/visual-evaluator.md)）禁止执行 `shell`、禁止套娃派生子代理（`subagent: "*" -> deny`）、禁止改业务代码（仅允许写 `.opencode/ultracode/QA_REPORT.md` 和 `qa/**`），并独占 `ultracode_playwright_*` 浏览器工具。


2. **开箱即用的 Playwright 独立视觉评审环（精准命中你的前端 UX/审美痛点）**
在 [`opencode.example.jsonc`](https://github.com/PlutoKeating/Project.UltraCode/blob/main/packages/config/opencode.example.jsonc) 和 `runtime.ts` 中，UltraCode 默认禁用了全局的 `ultracode_playwright_*`，仅放行给独立子代理 `visual-evaluator` 通过 `ultracode _mcp` 拉起本地 `@playwright/mcp`（`0.0.86`）进行真实页面点击、截图和响应式检查，并强制对照 `UI_RUBRIC.md` 按 `PASS / FAIL / NOT_VERIFIED` 评分（**任一硬门控失败即一票否决整个 Sprint**）。
3. **双轨制长程续跑机制（会话内 Checkpoint + 会话外 Ralph Worktree）**
* **会话内断点续跑（[`server.js`](https://github.com/PlutoKeating/Project.UltraCode/blob/main/packages/config/opencode/conversation/server.js)）**：注册 `ultracode_checkpoint` 工具并监听 `experimental.idle` 钩子。当主代理空闲且没有后台任务或原生 `/goal` 激活时，自动注入合成指令（`Continue the authorized goal from the latest handoff: ...`）推着往下走，同时内置熔断器（最多 25 轮、连续 3 次同里程碑停滞即熔断），并在用户新发 `prompt` 时立刻让位。
* **跨会话全新窗口循环（[`ralph.ts`](https://github.com/PlutoKeating/Project.UltraCode/blob/main/packages/installer/src/ralph.ts) + [`ralph/prompt.md`](https://github.com/PlutoKeating/Project.UltraCode/blob/main/packages/config/opencode/ralph/prompt.md)）**：`ultracode ralph run` 强制校验当前目录为独立 Git Worktree，封装了 `@th0rgal/ralph-wiggum`（`1.3.1`），强制每轮**仅做 1 个顶层任务、严格 TDD、写完更新 `.ralph/PROGRESS.md` 与 `.ralph/HANDOFF.md` 并做 1 次本地 Git Commit**，通过 `<promise>BLOCKED</promise>` 等退出信号驱动全新上下文循环。


4. **全端统一的权限/方向热切换（[`gui.tsx`](https://github.com/PlutoKeating/Project.UltraCode/blob/main/packages/plugin-gui/src/gui.tsx) + [`settings.js`](https://github.com/PlutoKeating/Project.UltraCode/blob/main/packages/config/opencode/conversation/settings.js)）**
通过 `server.js` 的 `permission.hook("evaluate")` 钩子，默认开启 `permissions: "auto"`（把 `ask` 自动转 `allow`，但保留 `git push`、`git reset --hard`、`rm -rf` 等显式 `deny/ask` 防线）和 `direction: "manual"`（遇到关键架构分叉时暂停发多选卡片询问），且 TUI、Desktop（`ComposerPill`）和 Web/Mobile 的 `/approvals`、`/direction` 实时同步。

### 二、 对标 Claude Code 第一性原理护城河：UltraCode 复刻了多少？

对照上一轮拆解的 Claude Code 四大核心护城河，UltraCode 的真实实现度如下：

| 护城河维度 | Claude Code + Claude 5 原生机制 | UltraCode (`v1.1.0`) 源码真实实现 | 复刻度与理论有效性评估 |
| --- | --- | --- | --- |
| **模型与 Harness 的 RL 联合对齐** | 工具调用、子代理派发、渐进式披露已刻入 Claude 5 权重，删减 80% 提示词依然稳定 | 无模型权重控制权，完全依赖 `agents/*.md` 提示词 + `obra/superpowers` 技能约束驱动 Gemini/DeepSeek | **未复刻（物理限制）**：对非 Claude 模型的指令遵从度仍高度依赖模型本身素质 |
| **上下文压缩与防腐烂引擎** | 8 级级联压缩（50KB 工具输出落盘、Snip、缓存级微压缩、83.5% Fork 子代理 9 段式摘要）+ 3 层记忆 | 未重写任何压缩逻辑，直接复用 OpenCode V2 原生压缩（仅在示例配置中设为 `keep: 15000 tokens, buffer: "15%"`） | **极弱**：单会话跑超长上下文时，仍可能撞上 OpenCode 原生压缩边界 Bug（如 [#57187](https://github.com/anomalyco/opencode/issues/57187)、[#48827](https://github.com/anomalyco/opencode/issues/48827)） |
| **解决上下文焦虑与跨窗口续命** | 训练期消除焦虑 + Context Reset 交接 | `ultracode ralph run` 每次迭代彻底重开全新会话，靠磁盘 `HANDOFF.md` / `FEATURE_LIST.json` / Git 交接 | **高度有效（绕道超车）**：用外部全新窗口替代单会话硬撑，非常适合你手头无限额度的 Gemini 4 |
| **前端 UX/UI 审美防自评偏差** | Anthropic 官方论文验证的 Planner + Generator + Playwright Skeptical Evaluator 三角制衡 | 完整复刻：`planner.md` 写 `SPRINT_CONTRACT.md` → `implementer.md` 编码 → `visual-evaluator.md` 挂 Playwright 跑 `UI_RUBRIC.md` | **高度复刻且有效**：这是 UltraCode 最具工程含金量、最直接解决你痛点的部分 |

还要特别指出的一个**源码级隐患**：在 UltraCode 所有的 `agents/*.md` 和 `opencode.example.jsonc` 中，**都没有配置任何 `model:` 字段**。这意味着如果你直接安装使用，规划、编码、检索和视觉评审默认全都在跑同一个模型——你必须在安装后手动为不同角色绑定 Gemini 4 Carbon / Neon / Hydrogen，才能发挥分层路由的威力。

### 三、 实话实说：UltraCode 能不能撑住你预期的“8–9 小时全量实现不烂尾”？

答案需要拆成**两种运行模式**来看，不能一概而论：

1. **如果你指望像用纯血 Claude Code 那样，在一个 `UltraBuild` 交互式长对话里一竿子跑 8–9 小时：大概率还是会“虎头蛇尾”。**
* **硬上限卡死**：`server.js` 源码中写死了 `MAX_CHECKPOINT_ROUNDS = 25` 和 `MAX_CHECKPOINT_STALLS = 3`，且 `BOOT_ID` 绑定当前进程生命周期（服务一重启，未完成的 Checkpoint 直接清空）。它设计的初衷是“防偷懒助推”，不是 9 小时无人值守引擎。
* **单窗口腐烂风险**：单会话跑 8–9 小时必然反复触发 OpenCode 原生压缩。OpenCode V2 社区在 2026 年 10–11 月仍有不少非 Claude 模型下的压缩摘要预算塌缩（[#57187](https://github.com/anomalyco/opencode/issues/57187)）和工具循环/子代理末段丢失（[#36670](https://github.com/anomalyco/opencode/issues/36670)）的 Issue，Gemini 4 在单一超长会话压缩多次后依然容易丢失全局约束。


2. **如果你切换到 `ultracode ralph run` 模式 + 前置 `UltraPlan` 契约：理论上完全可以实现接近甚至超越单会话 8–9 小时的交付稳定性。**
* **机制对齐你的需求**：你提到“提前把所有问题全部确定好、Spec 足够明确”。只要你先用 `UltraPlan`（或 Claude Code）把需求拆成细粒度的任务清单、`FEATURE_LIST.json` 和 `SPRINT_CONTRACT.md`，再在 Git Worktree 中启动 `ultracode ralph run`，**每一轮都是 0 历史包袱的干净上下文窗口**，每次只攻克 1 个模块并强制跑通单测和 `visual-evaluator` 的 Playwright 检查才 Commit。
* **必须调大的参数**：源码 `ralph.ts` 默认把 `maxIterations` 设为 `"20"`。对于你这种全栈多页面重构或从零到一的大项目，20 轮肯定不够跑 8–9 小时，启动时必须显式传更大的迭代上限（例如 `--max-iterations 80` 或 `100`），配合你的无限额度 Gemini 4 才能真正把全量功能啃完。
