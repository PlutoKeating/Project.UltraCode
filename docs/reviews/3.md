# UltraCode 对 Claude Code 核心工程能力复刻程度的深度审计

> **审计基准日：2026-11-24。** 目标为 `PlutoKeating/Project.UltraCode` v1.1.1，固定提交 `df0a165c3aa2317d27904ea9b6f4a5427df55ba8`；OpenCode 对照为 `dev` 分支固定提交 `a9156f58ea38442c4a8adac8fd1c83ac7272a56f`。本报告同时审阅官网、README、核心实现、角色提示词、模板与测试代码，并以 Anthropic 当前公开工程资料及社区方法作为外部参照([UltraCode](https://github.com/PlutoKeating/Project.UltraCode/tree/df0a165c3aa2317d27904ea9b6f4a5427df55ba8), [OpenCode](https://github.com/anomalyco/opencode/tree/a9156f58ea38442c4a8adac8fd1c83ac7272a56f))。

## 执行摘要

**直接结论：UltraCode 是有实质价值的 OpenCode 工程增强，但不能认定为对 Claude Code 最核心高水准能力的“充分复刻”。** 它最成功之处，是把 Anthropic 早期长任务 harness 的关键经验——明确验收标准、功能清单、一次只推进一个有界任务、真实测试、Git／进度文件交接、独立评估与浏览器 QA——组装成一套默认可用的 Goal Engineering 工作流；这些设计在理论上确实能降低目标漂移、上下文腐烂、提前报完成和生成者自评宽容([Anthropic 长任务](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [UltraCode Ralph](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/ralph/prompt.md))。然而，它并未重新实现 OpenCode 的 agentic loop、后台子代理、压缩或权限系统，自有 checkpoint 也没有独立完成裁判；与 Claude Code 当前按任务动态生成 JavaScript harness 的 Workflow 相比，更缺少通用运行图、脚本化中间状态、可组合的大规模并行与对抗验证机制([OpenCode goal](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/plugin/goal.ts), [Claude Workflows](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code))。

针对用户最关心的三个问题，可以压缩为下表。这里的“能力提升”指架构和机制带来的合理预期，不等同于已经实测获得的通过率；“同等实现”则必须同时满足工作持续性、结果完整性、验证可靠性、恢复能力和成本可控性，不能仅凭运行了八九个小时或派遣了很多代理来判定。

| 核心问题 | 审计结论 | 置信度与关键限定 |
|---|---|---|
| 相对原版 OpenCode 有什么新亮点？ | **有清晰增量**：前置澄清与交付型主角色、五类专家预设、Sprint／功能／进度／交接工件、无模型自动里程碑、Ralph fresh-context、独立代码与视觉审查、真实 Chromium、跨端控制与统一安装([README](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/README.md))。 | **高**，均能从源码定位；但 agent loop、子代理、压缩和权限主要继承上游，不能重复计为 UltraCode 创新。 |

## 1. 审计口径：先定义“第一性本质”，再比较组件

### 1.1 证据分层，避免把宣传当成能力

本审计把证据分成四层：**文档宣称**只说明项目希望提供什么；**程序实现**说明系统无论模型是否自觉都会执行什么；**提示词与模板**说明模型被要求做什么，但遵守具有概率性；**外部实证**才说明这些机制在真实任务上是否提升成功率、降低成本或减少人工监督。Claude Code 官方最佳实践也明确区分非确定性指令与确定性机制：提示词、`CLAUDE.md` 和技能依赖模型遵守，而 hook、deny 规则、测试和 CI 才由 harness 强制执行([Claude 最佳实践](https://www.anthropic.com/engineering/claude-code-best-practices))。因此，本报告不会因为 UltraCode 的 reviewer 提示词写着“必须 REJECT”就把它当作不可绕过的质量门禁，也不会因为模板存在 `passes: false` 就认定功能状态不可能被提前勾选。

研究范围覆盖 UltraCode 的 conversation 插件、七个角色、Ralph 启动器与提示词、功能和交接模板、Playwright 配置、运行时依赖与相关测试；OpenCode 侧覆盖 `session/runner/llm.ts`、`plugin/goal.ts` 及其裁判提示词、后台子代理任务与回报、嵌套深度和压缩实现。测试代码用于验证设计意图和边界，但**本环境没有 Bun，未实际执行项目测试，因而本报告不宣称测试通过**；结论是静态源码审计和公开资料交叉验证，而不是端到端基准结果([UltraCode 测试](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/installer/tests/conversation.test.ts))。

### 1.2 长任务能力的最小充分结构

从第一性原理看，长时间代理不是把聊天历史无限延长，而是一个持续控制系统：**目标表示 \(G\)** 定义完成条件；**外部状态 \(S_t\)** 保存代码、Git、任务和证据；**执行器 \(A_t\)** 通过模型与工具改变环境；**观察与验证器 \(V_t\)** 返回真实反馈；**调度器 \(C_t\)** 决定继续、分解、等待、恢复或停止。可以把它概括为 \(S_{t+1}=A(S_t,G,V_t)\)，下一步由 \(C(G,S_{t+1},V_{t+1})\) 决定，而不是由“模型说自己完成了”决定。Anthropic 对长任务的失败分析恰好对应这个结构：一次做太多会造成半完成状态，后来实例看到已有成果会提前宣布完成，单靠压缩又会丢失关键要求，所以需要功能清单、增量进展、Git 和进度文件来跨越上下文([Anthropic 长任务](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents))。

多代理只是这个控制系统的一种执行策略，不是独立护城河。它只有在任务能分解为独立工作单元、各单元拥有干净上下文、编辑范围不重叠、验证器能定位失败、合并成本低于并行收益时才有效。Anthropic 的并行 C 编译器实验中，16 个代理在大量独立失败测试上容易并行，但面对 Linux 内核这一巨大耦合目标时会反复修同一个错误并覆盖彼此；直到引入 GCC 作为已知正确参照并把失败定位到不同文件，并行才重新有效([C 编译器实验](https://www.anthropic.com/engineering/building-c-compiler))。所以“倾向派更多子代理”不是目标本身，**可分解性、任务所有权、验证分辨率和合并纪律**才是。

| 第一性失效模式 | 必需的 harness 机制 | 不能替代该机制的表面组件 |
|---|---|---|
| 需求错误或完成定义模糊 | 前置澄清、可观察验收标准、排除项 | 更长的系统提示词 |
| 上下文腐烂、目标漂移 | 外部规范、结构化交接、fresh context、压缩后目标重注 | 单纯扩大上下文窗口 |
| 提前报完成、自评宽容 | 独立裁判、真实测试、证据门禁 | 模型自述“已经全部完成” |
| 多代理重复劳动与冲突 | 独立任务、所有权、隔离 worktree、合并协议 | 无约束地增加代理数量 |
| 中断后无法恢复 | 持久化状态、幂等恢复、后台看门狗、明确恢复入口 | 仅在内存中保存待办事项 |
| 成本与延迟失控 | 轮次／预算／停滞上限、按价值路由并行 | 把更多 token 当作更高质量 |

## 2. OpenCode 原生底座：UltraCode 不必重写的部分

### 2.1 真正的 agentic loop 与上下文恢复

OpenCode 的核心执行器已经实现完整循环：每轮处理 inbox、加载上下文、执行模型步骤和工具调用，在会话即将 idle 时触发 `experimental.idle`；插件若能注入新的 synthetic input，同一 execution 就可继续。它还处理自动压缩、上下文 overflow 恢复和后台摘要预计算，并在输出达到 token 上限时自动续写，连续三次 `length` 后才报错([OpenCode loop](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/session/runner/llm.ts))。UltraCode 的 checkpoint 正是挂在这个 idle 钩子上，因此它是**上游循环的一个插件消费者**，不是另一套 agentic loop。

OpenCode 压缩器默认保留 15,000 tokens、预留 15% 空间，摘要模板包含 Objective、Requirements、Decisions、Work State、Next Move、Relevant Files 和 Important Context，并支持 overflow 触发和后台预计算([OpenCode compaction](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/session/compaction.ts))。UltraCode 示例配置中的相同保留值与 15% buffer 主要是把上游能力显式配置出来，而不是自研压缩算法([UltraCode 配置](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode.example.jsonc))。这并不削弱 UltraCode 的价值，但评估“新亮点”时必须把继承与新增分开。

### 2.2 后台子代理与原生 `/goal` 被低估了

OpenCode 子代理本来就在独立 child session 和 fresh context 中后台运行，完成后通过 synthetic notice 向父会话 inbox 投递报告并唤醒父会话；默认嵌套深度为 1，服务器关闭不会直接释放 child claim，后续启动可以恢复相关执行([OpenCode agents](https://opencode.ai/docs/agents/), [子代理回报](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/session/execution/subagent-report.ts), [深度限制](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/session/subagent-depth.ts))。UltraCode 的增量是为主代理预设“何时派谁、权限如何、返回什么证据”的角色目录和委派纪律，而不是创造后台子代理能力。

更重要的是，OpenCode 原生 `/goal` 已比 UltraCode 自有 checkpoint 更接近“目标裁判”：每轮调用独立 reviewer，依据工具结果、命令输出和文件内容返回 `done／continue／blocked／paused／wait`，并支持后台工作等待、30 分钟无活动看门狗、50 轮上限、3 次无进展停止以及裁判上下文溢出后一次压缩重试([OpenCode goal](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/plugin/goal.ts))。其裁判提示词明确写道“assistant claiming the goal is met is not evidence”，疑则继续([goal judge](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/plugin/goal/judge.txt))。UltraCode 检测到官方 `/goal` active 时会清除自己的 checkpoint 并避让，这既避免双循环冲突，也说明两者存在功能重叠([UltraCode server](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/conversation/server.js))。

## 3. UltraCode 的真实增量与实现边界

### 3.1 从通用编码会话变成“目标工程交付团队”

UltraBuild 主角色要求小任务直接完成，广泛探索时委派独立搜索，多文件或模糊任务先建立可审查计划、验收标准和真实 QA 场景；实现单元必须边界清楚且编辑不重叠，复杂或面向用户的改动在宣布完成前应取得独立 reviewer 或 visual-evaluator 结论([orchestrator](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/agents/orchestrator.md))。planner 先读仓库再提问，只询问会实质改变范围、不可逆决策、支出或验收的内容，并要求 sprint contract 和恢复指引；implementer 一次只接受一个有界目标，不得扩大范围或削弱验收；reviewer 必须看真实 diff，视觉评估者必须操作运行中的产品([planner](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/agents/planner.md), [implementer](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/agents/implementer.md))。

这套设计的价值不在于提示词更长，而在于**默认业务流从“回答用户”转向“定义目标—分解—实现—独立验证—交接”**。它能改善用户描述的“提前澄清所有问题”体验，但准确说法是“批量澄清所有会改变交付的关键不确定项”，而不是数学意义上的所有问题；planner 明确反对为无关细节反复打扰用户([planner](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/agents/planner.md))。同时，这些角色大多仍是模型遵守的非确定性指令：权限能限制写文件和再派子代理，却不能保证主代理一定先规划、一定派遣评审或一定拒绝不合格结果，因此应视为强烈的工作流先验，而非确定性 DAG 调度器。

### 3.2 外部工件与 Ralph：最接近 Anthropic 长任务本质的部分

UltraCode 的 `FEATURE_LIST.json` 把功能定义为可观察行为、操作步骤、验证命令和初始为假的 `passes`；Ralph 每轮先读 Git、`.ralph/PROGRESS.md`、`.ralph/HANDOFF.md`，以及存在时的 `FEATURE_LIST` 与 `SPRINT_CONTRACT`，随后只处理一个顶层任务，先建立 baseline，再执行真实验收、更新证据并创建一次本地提交([功能模板](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/ralph/templates/FEATURE_LIST.json), [Ralph prompt](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/ralph/prompt.md))。这与 Anthropic  initializer／coding-agent 模式中的功能清单、单功能增量、Git 历史和进度日志高度同构，针对的正是“一次做太多、后一个会话猜测状态、未测试就勾完成”三个根本故障([Anthropic 长任务](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents))。

启动器强制使用专用 linked Git worktree，要求 `.ralph/ralph-tasks.md`，默认最多 20 次迭代，并调用固定来源的外部 `@th0rgal/ralph-wiggum`，参数包含 `--abort-promise BLOCKED`、`--no-commit` 和 `--no-allow-all`([Ralph 启动器](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/installer/src/ralph.ts))。这意味着 Ralph 是项目集成和约束过的外部循环，而非从零实现的代理内核。还有一个实际使用边界：启动器自动复制 PROGRESS、HANDOFF 和忽略文件，但不会自动把 FEATURE_LIST、SPRINT_CONTRACT 复制到目标项目；Ralph 提示词是在“存在时”读取它们，所以用户若希望获得完整 Anthropic 式功能门禁，需要确保这些工件已被规划阶段实际生成并放在约定位置([Ralph 启动器](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/installer/src/ralph.ts), [Ralph prompt](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/ralph/prompt.md))。

### 3.3 独立 reviewer、真实 Chromium 与跨端控制

reviewer 被要求以怀疑态度检查真实 diff 和验收标准，只有所有硬标准均有证据且无阻断问题才 `APPROVE`；visual-evaluator 要导航、点击、填写、缩放并检查截图，对硬门槛失败直接拒绝，同时只能写 QA 报告与 artifacts，不能修改实现、测试或验收标准([reviewer](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/agents/reviewer.md), [visual-evaluator](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/agents/visual-evaluator.md))。配置还接入 Playwright MCP，执行超时为 600,000ms，安装运行时默认使用隔离 Chromium([UltraCode 配置](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode.example.jsonc), [runtime](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/installer/src/runtime.ts))。这比仅让生成者阅读自己的代码或运行单元测试更接近真实用户反馈，尤其能暴露界面 wiring、响应式和交互路径问题。

跨 Terminal、Desktop、Web 和 Mobile 的状态同步、审批和方向问题控制，以及统一安装升级，也是相对裸 OpenCode 的可见产品增量([README](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/README.md))。它们不直接提高模型推理质量，却能降低长任务的人工监督摩擦：用户可以在不同客户端转向、清除里程碑或调整审批，权限自动模式只把 `ask` 改成 `allow`，显式 `deny` 保持不变([UltraCode server](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/conversation/server.js))。不过“独立 reviewer”依然是一个由模型生成判断的子代理，不是测试 CI 式硬门禁；视觉评价也受浏览器工具可观察性、评分 rubric 和评估模型自身偏差约束。

### 3.4 自有 checkpoint：有用，但比宣传措辞更保守

conversation 插件让主模型通过 `ultracode_checkpoint` 保存“下一里程碑”，会话 idle 且无后台工作时注入“Continue the authorized goal from the latest handoff”，新用户 prompt 会清除检查点，相同里程碑连续三次或累计 25 轮会熔断([UltraCode server](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/conversation/server.js))。这是有价值的产品化：用户不必显式输入 `/goal`，清晰的长交付目标即可自动续跑，而且用户转向时立即让路。它解决的是“模型一轮结束后没人再按继续”的问题，并以防停滞和轮次上限控制失控循环。

但它没有调用独立 reviewer 来判断目标是否完成，保存的下一里程碑来自当前主模型自己；`BOOT_ID` 用于识别进程，启动和 idle 时会清理旧启动 ID 的 checkpoint，因此**进程重启后不会从 checkpoint 静默自动续跑**，只能依靠仓库 handoff 等文件恢复。测试代码明确覆盖持久化、idle synthetic、旧 BOOT_ID 清理、25 轮上限、3 次停滞和 `/goal` 共存，说明这些不是外部猜测，而是当前设计边界([UltraCode 测试](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/installer/tests/conversation.test.ts))。OpenCode 原生 `/goal` 在重启后也会把 active goal 置为 paused，需用户 `/goal resume`，所以两者都提供“可恢复”而非无条件自治重启([OpenCode goal](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/plugin/goal.ts))。

| 续跑维度 | UltraCode checkpoint | OpenCode 原生 `/goal` |
|---|---|---|
| 激活方式 | 清晰长目标下由主模型自动设置下一里程碑([server](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/conversation/server.js)) | 用户显式 `/goal <objective>`([goal](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/plugin/goal.ts)) |
| 完成／继续判断 | 主模型自己更新下一里程碑，**无独立目标裁判** | 独立 generate reviewer 依据证据给出结构化 verdict |
| 轮次与停滞 | 25 轮、同一里程碑 3 次 | 50 轮、3 次无进展 |
| 后台等待 | 有后台工作时不注入继续 | 支持 `wait`，并有 30 分钟看门狗 |
| 用户转向 | 新 prompt 清除 checkpoint，立即让路 | 可 paused／resume／clear |
| 重启 | 旧 BOOT_ID checkpoint 被清理；从 handoff 人工恢复 | active 变 paused，显式 `/goal resume` |
| 二者同时存在 | 官方 `/goal` active 时 UltraCode 避让 | 原生机制继续工作 |

## 4. 对 Claude Code 护城河的复刻评分

### 4.1 对 Anthropic 早期长任务 harness：针对性强

若比较对象是 Anthropic 公布的 initializer＋coding-agent 长任务方法，UltraCode 的复刻是明确且有针对性的。功能清单把高层需求转成可观察功能，Ralph 一次只做一个顶层任务，Git 提交、PROGRESS 和 HANDOFF 把记忆移出聊天上下文，真实浏览器和独立 reviewer 则分别补足环境反馈和生成者自评偏差([Anthropic 长任务](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [UltraCode Ralph](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/ralph/prompt.md))。Anthropic 后续的 planner—generator—evaluator 工作流还强调 sprint contract、生成与评价分离、真实 Playwright 操作和结构化文件通信，UltraCode 对这些也有直接对应([长应用 harness](https://www.anthropic.com/engineering/harness-design-long-running-apps))。

因此，从机制方向看，**预期能力提升是合理的**：目标外置减少压缩后的漂移，小步交付降低半完成状态，fresh context 缓解历史污染，独立评估增加发现遗漏的机会，真实界面操作补足“代码看起来对但产品不能用”的盲区。可是 Anthropic 也报告了这些方法的成本：一个完整 harness 示例运行 6 小时、花费 200 美元，而单代理示例为 20 分钟、9 美元；评估器仍需 few-shot 校准，分数会平台化，最终产物仍可能存在产品直觉和边界情况缺陷([长应用 harness](https://www.anthropic.com/engineering/harness-design-long-running-apps))。UltraCode 复制了结构，并不等于复制了评估器调校、任务环境和模型表现。

| Claude 公开方法 | UltraCode 对应物 | 复刻判断 |
|---|---|---|
| 全面功能清单，初始全部失败 | `FEATURE_LIST.json`，含 steps、verification、`passes:false` | **强对应**；但状态变更主要依赖模型纪律，无独立程序防提前勾选 |
| 每会话只做一个功能 | Ralph 每轮一个顶层任务 | **强对应** |
| Git、progress 文件、干净状态 | 单提交、PROGRESS、HANDOFF、baseline 检查 | **强对应** |
| 真实浏览器端到端测试 | Playwright MCP＋visual-evaluator | **强对应**；覆盖与视觉能力仍有限 |
| 生成者与评估者分离 | implementer 与 reviewer／visual-evaluator | **中强对应**；提示词门禁非完全硬约束 |
| sprint 前协商完成定义 | planner 生成 sprint contract、QA 场景和排除项 | **中强对应**；未见确定性双方协议状态机 |
| fresh context 跨会话交接 | 外部 Ralph 循环＋仓库工件 | **强对应** |
| 独立目标裁判决定 continue／done | UltraCode checkpoint 无；可避让并使用 OpenCode `/goal` | **自有机制不足，组合上游后部分补足** |

### 4.2 对当前 Claude Code 动态 Workflow：不是同一种编排层级

Claude Code 当前动态 Workflow 允许模型**按任务现场编写 JavaScript harness**，以 `agent()` 创建子代理，以 `parallel()`、`pipeline()` 和 `phase()` 组合工作，并让计划与中间结果驻留在脚本而非单一聊天上下文中；官方列出的模式包括 fan-out-and-synthesize、adversarial verification、generate-and-filter、tournament、loop until done，以及分类路由和模型选择([Claude Workflows](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code))。中断后恢复会话可以继续工作流，脚本还能决定代理模型和 worktree 隔离。这是从“固定角色提示词驱动主代理自由委派”上升到“任务专用、可执行、可恢复的运行图”。

UltraCode 没有等价的动态 JavaScript 编排器。其多代理是 orchestrator 根据提示词选择预设角色，禁止重叠编辑并要求独立评审；Ralph 是固定的一次一任务 fresh-session 循环。二者都可能取得好结果，但表达力不同：UltraCode 适合软件交付的通用纪律，动态 Workflow 能为 50 个独立审查项、每个主张一个核查器、竞争方案锦标赛或逐规则对抗验证生成专用拓扑([Claude Workflows](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code))。所以，不能因为 Claude Code 里也存在名为“ultracode”的 Workflow 触发词，就把本项目的 UltraCode 视为该机制的复刻；**同名不代表同构**。

### 4.3 模型—工具协同和实证缺口：组件清单无法证明同等效果

Claude Code 的体验还来自模型默认策略、工具接口、权限分类、压缩质量、评估器校准和反馈环境之间的协同。外围项目可以复制工具名称和角色提示词，却不能仅凭源码证明其任意 Provider／模型组合都具有相同的任务分解、工具调用可靠性、视觉判断或长程坚持能力。UltraCode 的 provider／model-neutral 是可用性优势，却同时意味着效果方差会随所选模型显著变化；对于社区逆向资料中“Claude 经过专门工具协同或强化学习训练”的解释，只能视为开发者假说，不能当作 Anthropic 已确认训练事实。

现有实证也提醒不要把复杂 harness 直接等同于更高通过率。2026 年《The Scaffold Effect in Coding Agents》在两个模型、三个开源 harness、50 个 Terminal-Bench Pro 任务上发现，每解决任务 token 最高相差 40 倍，而同模型配对通过率差异多为 0–8 个百分点；不同 harness 还呈现可跨模型复现的失败指纹([Scaffold Effect](https://arxiv.org/abs/2607.22585))。这并不否定 UltraCode 的设计，而是说明最终评估必须同时报告成功率、token、延迟、人工干预和失败类型。当前未见 UltraCode 针对裸 OpenCode、OpenCode＋`/goal`、Claude Code 的同模型同任务同预算公开对照，因此“理论有效”可以成立，“同等高水准效果”证据不足。

### 4.4 社区复刻与逆向资料应如何使用

社区中的 Claude Code 逆向仓库、系统提示词整理和解除限制项目，能帮助提出“可能存在哪些工具、提醒和循环”的假设，却不能替代当前官方文档或目标项目源码。本研究把这类材料仅用于发现审查线索，例如检查停止钩子、子代理提醒、压缩和权限边界，最终结论仍回到固定提交实现与官方工程文章([逆向示例](https://github.com/isheng-eqi/claude-code-reverse-engineering), [提示词整理](https://github.com/xiufengsun/claude-code-prompt), [社区实验](https://github.com/TKasperczyk/claude-unbound))。尤其不能把某次版本反编译得到的提示词当成永久架构，也不能由提示词相似推出模型行为相同。

Ralph 社区方法提供的有效洞见，是把每一轮当作新工程师接班：只取一个小任务，把真实进展留在 Git 和文件里，通过外部循环不断创建新鲜上下文，而非祈求一个无限会话记住一切([Ghuntley Ralph](https://ghuntley.com/ralph/), [实践仓库](https://github.com/ghuntley/how-to-ralph-wiggum))。UltraCode 对这一方法的集成是认真的，包含 worktree、任务文件、baseline、验证证据、handoff 和熔断；但社区循环同样不是质量保证器，若任务列表错误、测试失真或完成信号由模型误判，循环只会更快地放大错误。因此真正值得复刻的是**外部状态＋环境反馈＋小步恢复**，不是“while true”本身。

## 5. 对用户三个核心问题的最终回答

### 5.1 相对原版 OpenCode，显著亮点与预期提升是什么？

最重要的亮点是**把上游通用能力组织成有默认交付纪律的系统**。原版 OpenCode 已提供 loop、后台子代理、角色权限、技能、压缩和 `/goal`，用户需要自己决定何时规划、派谁、如何交接和凭什么完成；UltraCode 则把这些选择预编成两个主角色、五类专家、验收与 QA 模板、自动里程碑和 Ralph 工作流([OpenCode agents](https://opencode.ai/docs/agents/), [UltraCode README](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/README.md))。这能降低用户编写高质量提示词和搭建脚本的门槛，也能减少每次任务重新发明流程的 variance。

预期收益主要体现在过程质量，而非基础推理能力的突然跃升：前置关键澄清降低错误目标上的无效工作，独立搜索与实现角色隔离上下文和编辑范围，工件化交接降低跨会话重建成本，独立 reviewer 和真实浏览器增加失败被发现的机会，跨端控制降低长任务监督摩擦。与此同时，自有 checkpoint 并非对原生 `/goal` 的全面升级；如果用户愿意显式使用 `/goal`，OpenCode 原生的独立裁判和后台等待反而更强。最合理的部署理解是“**UltraCode 默认体验层＋OpenCode 原生目标裁判可按场景组合**”，而不是所有自制组件都优于上游。

| 能力项 | OpenCode 原生 | UltraCode 增量 | 预期净收益 |
|---|---|---|---|
| Agentic loop、工具回写、输出恢复 | 已有完整实现([loop](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/session/runner/llm.ts)) | 使用 idle hook，不重写 loop | 集成价值，非新内核 |
| 子代理 | 后台 child session、报告回收、权限 | 五类领域角色、任务边界和返回格式 | 降低委派决策成本 |
| 前置澄清 | 取决于用户提示和模型 | planner／orchestrator 默认批量问关键问题 | 减少错误假设和来回确认 |
| 目标持续 | `/goal` 独立裁判 | 无模式 checkpoint 自动续跑，遇 `/goal` 避让 | 默认体验更顺；裁判能力不增强 |
| 跨上下文记忆 | 自动／overflow 压缩 | Git＋功能＋进度＋handoff＋fresh Ralph | 显著降低对聊天历史的依赖 |
| 完成验证 | 工具、测试、权限及 `/goal` | 独立 reviewer、真实 Chromium、Sprint QA | 更容易发现漏项与界面故障 |
| 并行编排 | 原生后台子代理 | 提示词驱动的不重叠委派 | 有改善，但不是通用 DAG |
| 产品与运维 | 多客户端基础能力 | 统一安装、运行时固定校验、跨端 UltraCode 控制 | 降低部署与监督成本 |

### 5.2 按 Claude Code 第一性护城河，是否充分复刻并理论有效？

答案是：**复刻了关键子集，方向上理论有效，但整体不充分。** 充分复刻不能只看有没有功能清单、子代理和浏览器，而应看能否在任务变化时构造合适的控制图、能否把计划与中间状态外置、能否以独立证据决定继续或停止、能否在大规模并行时定位工作单元、能否在中断后恢复，以及模型和工具是否稳定协同。UltraCode 在前面几项中的“长任务记忆、小步实现、真实反馈、独立评审”得分较高，在“动态运行图、对抗组合、通用恢复、评估器校准和跨模型一致性”上仍有明显缺口。

这一判断并不否认 UltraCode 的工程质量。相反，它没有侵入式 fork OpenCode，而是利用角色、权限、插件、模板和外部 runner 组成可维护层，这是合理的架构选择；与上游 `/goal` 共存、用户转向即清除 checkpoint、停滞熔断和显式 deny 不被自动放行，都体现了对失控循环和用户主权的重视([UltraCode server](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/config/opencode/conversation/server.js))。更准确的定位是：**它复刻了 Claude Code 长任务工程经验的相当一部分“骨架”，但没有复刻当前动态 Workflow 的“可编程神经系统”，也没有证据复制 Claude 模型与工具链组合出的整体效果。**

| 护城河维度 | 复刻程度 | 审计理由 |
|---|---|---|
| 目标与验收外置 | 高 | Sprint、功能清单、验收场景和 handoff 均有实际模板与提示词 |
| 小步增量与干净提交 | 高 | Ralph 明确单任务、baseline、真实验证、单提交 |
| 跨上下文恢复 | 中高 | fresh session＋仓库工件很强；自动 checkpoint 重启即清理 |
| 独立完成裁判 | 中 | reviewer 角色存在；自有 checkpoint 无裁判，可靠上游 `/goal` 补足 |
| 真实环境反馈 | 高（Web 域） | Playwright 和 visual-evaluator 直接操作运行产品 |
| 多代理任务隔离 | 中 | 有不重叠编辑纪律和 worktree；无通用任务锁／DAG／合并调度器 |
| 动态任务专用 harness | 低 | 固定角色与固定 Ralph，不按任务生成 JS 工作流 |
| 大规模对抗验证 | 低至中 | 可人工提示多个评审，但无原生 tournament／fan-out 图和缓存恢复 |
| 模型—工具协同 | 无法认定 | 模型中立且缺少同模型对照，效果依赖具体 Provider |
| 成本与质量实证 | 未证明 | 未见公开同任务、同预算、同模型基准 |

### 5.3 能否同等实现“澄清—多代理—8–9 小时坚持完成”的体验？

**在有利条件下，UltraCode 有望接近其中一部分工作体验；作为一般性结论，不能同等保证。** 最有利的情形是需求能写成完整规范，功能可拆成独立验收项，项目有可靠测试与可启动环境，浏览器或 API 能观察主要行为，模型足以理解仓库，运行期间无配额和外部服务中断。此时，前置澄清减少返工，子代理并行搜索或实现独立单元，Ralph 不断用新上下文推进剩余任务，handoff 让中断后可继续，架构确实支持多小时自治。

不利情形则会把“持续运行”与“持续正确”分开。若需求本身模糊，提前澄清只能降低风险而不能消除未知；若所有代理都卡在同一个耦合 bug，更多代理会重复劳动；若测试无法区分对错，独立 LLM reviewer 也可能误放行；若主模型反复选择错误里程碑，checkpoint 没有独立裁判纠偏；若达到 25 轮、默认 20 次 Ralph 或 3 次停滞，系统会按设计停止；若进程重启，仍需从 handoff 或 paused goal 显式恢复([Ralph 启动器](https://github.com/PlutoKeating/Project.UltraCode/blob/df0a165c3aa2317d27904ea9b6f4a5427df55ba8/packages/installer/src/ralph.ts), [OpenCode goal](https://github.com/anomalyco/opencode/blob/a9156f58ea38442c4a8adac8fd1c83ac7272a56f/packages/core/src/plugin/goal.ts))。因此，“八九小时后仍有输出”不是完成证据，必须检查剩余功能、真实验收、未解决缺陷和人工接管次数。

| 长任务场景 | UltraCode 理论表现 | 是否可预期同等 Claude Code 体验 |
|---|---|---|
| 规范清晰的全栈 Web 应用，测试完整 | 最匹配：功能清单、Sprint、浏览器 QA、Ralph 全部发挥作用 | **有望接近部分体验**，仍取决于模型与评估器 |
| 大量独立迁移、审查或研究子任务 | 可派子代理，但固定角色不如动态 fan-out 图灵活 | **不宜声称同等**，并行拓扑和中间状态外置较弱 |
| 强耦合调试、单一线索根因分析 | 多代理收益有限，checkpoint 可能重复错误方向 | **不能保证**，独立验证和假设竞争需额外设计 |
| 需求持续变化、用户频繁转向 | 新 prompt 清除 checkpoint 是优点，可避免旧目标绑架 | **控制体验较好**，但完成范围需重订 |
| 跨进程重启的多小时任务 | handoff 可恢复，checkpoint 不自动跨 BOOT_ID | **可恢复非无缝自治**，需明确恢复步骤 |
| 验证稀缺的主观设计或开放研究 | reviewer／rubric 有帮助，但评价偏差和遗漏仍大 | **证据不足**，不能用时长替代质量 |

## 6. 要把“理论有效”推进到“高水准可信”，还缺什么？

### 6.1 优先补强确定性验证与恢复，而不是继续堆角色

第一优先级应是让完成状态由独立证据推进：功能项绑定可执行检查，reviewer  verdict 与 CI 结果结构化保存，未通过时程序禁止翻转 `passes`；在通用目标层优先复用或增强 OpenCode `/goal` 的证据裁判，而不是让主模型自己不断决定下一里程碑。第二优先级是统一恢复语义：checkpoint、Ralph 和 `/goal` 应有同一个持久化运行状态，明确区分“进程内自动续跑”“重启后人工确认恢复”和“后台任务等待”，避免用户把 handoff 可恢复理解为无人值守自动重启。

第三优先级才是更丰富的编排。可以从软件交付中最常见的图开始：独立任务 fan-out、每实现一个 verifier、合并前回归、失败后 delta 定位、无新发现时停止；每个节点记录输入、输出、模型、成本、工件哈希和重试次数，使运行图可恢复、可审计。多代理应设置任务锁、所有权和合并协议，并根据验证器能否区分独立失败来决定并行度。Anthropic 的编译器实验说明，验证环境往往比代理数量更决定自治上限([C 编译器实验](https://www.anthropic.com/engineering/building-c-compiler))。

### 6.2 用对照实验验证“接近”，不要靠体验叙事

建议至少设置四组：裸 OpenCode 默认会话、OpenCode＋原生 `/goal`、UltraCode checkpoint／Ralph、Claude Code 默认或动态 Workflow；在同一模型可接入的组之间保持模型、温度、任务、初始仓库、工具、时间和 token 预算一致，并重复多次。指标除最终通过率外，还应包括完成需求比例、独立隐藏测试、人工澄清与接管次数、无效轮次、合并冲突、token／美元、墙钟时间、重启恢复成功率和错误报完成率。Scaffold Effect 的研究设计正说明，只报模型和 pass rate 会掩盖巨大的成本与失败模式差异([Scaffold Effect](https://arxiv.org/abs/2607.22585))。

任务集需要覆盖不同可验证性：有完整测试的 Web 功能、跨仓库迁移、强耦合调试、需求不完全明确的增量开发、浏览器视觉与交互 QA，以及中途 kill／restart 的恢复场景。只有在这些任务上，UltraCode 相对 OpenCode＋`/goal` 显示稳定增量，并在同模型条件下接近 Claude Code 的完成率、验证可靠性和监督成本，才能把“架构有针对性”升级为“高水准复刻有效”。当前源码足以支持前者作为合理假说，不足以支持后者作为事实。

| 验证维度 | 必报指标 | 要排除的假阳性 |
|---|---|---|
| 完成质量 | 隐藏测试、需求覆盖率、阻断缺陷数 | 代理自称完成、只跑公开测试 |
| 持续性 | 有效进展轮次、停滞次数、目标漂移次数 | 空循环、重复读文件、长时间无状态变化 |
| 多代理收益 | 独立任务完成数、冲突数、重复工作率 | 代理数量多但总吞吐更低 |
| 恢复能力 | kill 后恢复率、状态丢失、重复提交 | 只恢复聊天，不恢复后台运行图 |
| 成本 | token、费用、墙钟、缓存命中 | 用巨额计算换取微小通过率提升 |
| 人工负担 | 澄清、审批、纠偏、接管和最终审查次数 | 把人工隐形劳动算作“全自动” |

## 最终判定

**UltraCode 不是宣传空壳。** 其角色权限、Sprint／功能／进度／交接模板、真实浏览器 QA、Ralph fresh-session、用户转向让路、熔断与跨端控制都能在源码中定位，且与 Anthropic 公布的长任务失败模式有清楚因果对应。相对裸 OpenCode 默认使用方式，它很可能显著提升复杂软件交付的流程完整性、可恢复性和验证纪律，尤其适合规范清晰、可拆分、可真实测试的全栈任务。

**但“充分复刻 Claude Code 最核心高水准工程能力”仍然过强。** 它没有等价实现当前动态 Workflow 的任务专用 JavaScript harness 和可恢复并行运行图，自有 checkpoint 缺少 OpenCode 原生 `/goal` 已有的独立证据裁判，许多验收仍靠模型自律，且没有公开同模型同预算对照证明同等质量。对“提前澄清、倾向多代理、八九小时始终坚持完成”的体验，最严谨的表述是：**UltraCode 能系统性提高接近这种体验的概率，但不能保证同等实现，更不能保证任务最终完整、正确或更经济。**
