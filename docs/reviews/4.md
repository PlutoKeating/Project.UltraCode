基于对 **UltraCode（PlutoKeating/Project.UltraCode v1.1.1）** 官方仓库、官网、架构文档与关键源码（agents、conversation plugin、Ralph 模板、RESEARCH/ORIGIN_GOAL），以及对 **OpenCode V2（anomalyco/opencode）** 与 **Claude Code** 公开架构/社区逆向的对照，结论如下。

---

## 0. 项目本质定位（先定边界）

UltraCode **不是** 重写或 fork OpenCode 的新 harness，而是：

- **非侵入的 Goal Engineering 层**，挂在官方 OpenCode V2（≥2.3.2，已验证 2.4+）之上；
- 通过 **角色定义（primary + subagents）+ 插件（RPC/checkpoint/idle 续跑）+ Ralph 外层新会话循环 + Playwright 视觉 QA** 组合实现“长程目标工程”；
- **从不改官方二进制、不碰 API key**，可干净卸载。

因此：它复刻的是 **Claude Code 风格的工程方法论与编排习惯**，而不是 Claude Code 的完整 runtime harness（权限分类器、多级 compaction pipeline、原生 dynamic workflow 脚本运行时等）。

---

## 1. 相对原版 OpenCode：显著亮点与预期能力提升

| 维度 | 原版 OpenCode V2 | UltraCode 叠加后 |
|------|------------------|------------------|
| 主角色 | 内置 build / plan | **UltraBuild（交付）+ UltraPlan（只读规划）**，Shift+Tab 切换 |
| 子代理 | 通用 general/explore 等 | **固定专家链**：librarian / architect / implementer / reviewer / visual-evaluator（权限严格隔离，如 implementer 禁止再派子代理、reviewer 禁止 edit） |
| 长程续跑 | 依赖用户与 `/goal` 等 | **`ultracode_checkpoint` + `experimental.idle` 钩子**：自动推进里程碑；**BOOT_ID 围栏**防重启误续；**25 轮 / 3 次同里程碑停滞熔断**；与官方 `/goal` 互斥避让 |
| 跨会话交接 | 会话内为主 | **Ralph 模板**：HANDOFF / PROGRESS / FEATURE_LIST / SPRINT_CONTRACT / QA_REPORT + `ultracode ralph run`（linked worktree 新会话） |
| 视觉验收 | 需自配 | **独立 visual-evaluator + Playwright MCP**，强制真机点击与 rubric，写 QA_REPORT |
| 需求澄清 | 依赖模型自觉 | 编排提示强制**开工前批量选择题澄清**（orchestrator 明确要求用选择题卡一次问清） |
| 控制面 | 分散 | **全表面同步**：TUI / Desktop ComposerPill / Settings / Web·Mobile `/approvals` `/direction` |
| 工程纪律 | 可选 | 绑定 **Superpowers**（澄清、TDD、系统化调试）作为技能层 |

源码级依据（非宣传）：

- `packages/config/opencode/conversation/server.js`：checkpoint 存储、idle 自动 `synthetic` 续跑、权限 auto 放行、与 `opencode.goal` 共存逻辑、MAX_CHECKPOINT_ROUNDS/STALLS。
- `agents/*.md`：角色权限与“证据优于自评”的硬约束。
- `docs/ARCHITECTURE.md` / `docs/RESEARCH.md`：明确“子代理隔离会话内上下文，Ralph 负责顶层新会话，二者不可替代”。

**预期提升**：在 OpenCode 上把“会说完就停 / 半路跑偏 / 自己夸自己过”的概率压下去，并提供可恢复的长任务骨架；**不**改变 OpenCode 的核心 agent loop 实现。

## 2. 对照 Claude Code 护城河：是否针对性复刻、是否理论上有效？

### Claude Code 高能力的第一性原因（业界/官方/逆向共识）

1. **模型 × Harness 联合对齐**  
   Claude 家族在后训练里内化了“何时派子代理、何时压缩、如何不提前收工”；非 Claude 模型塞进同一 harness 常出现工具习惯错位、空子会话、早停。

2. **Agentic harness 厚度**  
   - 核心仍是 while 循环（模型决策 + 工具 + 结果回灌）；  
   - 真正差异在周边：**多级 compaction、权限闸门、subagent 隔离与编排、hooks、session 持久化、dynamic workflows（脚本化编排多 agent，中间结果不进主上下文）**。

3. **长程病理的对症设计**（Anthropic 公开研究）  
   - **Context anxiety** → 用 **context reset + 结构化 handoff**，而非无限撑长窗口；  
   - **Self-evaluation bias** → **Planner / Generator / 独立 Skeptical Evaluator** 分离 + Sprint Contract + 真浏览器验证。

4. **Dynamic workflows**  
   把编排逻辑写成可执行脚本（`agent()` / `parallel()` / `pipeline()`），主会话只收最终结果，避免目标漂移与上下文膨胀。

### UltraCode 的对应关系

| Claude Code 能力点 | UltraCode 是否做了针对性设计 | 理论有效性 |
|--------------------|------------------------------|------------|
| 激进派子代理、隔离上下文 | ✅ 专家 subagent + 权限 deny 再派/编辑 | **有效（在 OpenCode 原生 subagent 能力边界内）** |
| 独立评审、反自评宽容 | ✅ reviewer / visual-evaluator 独立、只读/只写报告 | **有效**，与 Anthropic GAN 式分离同构 |
| 真机 UI 验证 | ✅ Playwright MCP + UI rubric | **有效**（依赖 MCP 与运行环境） |
| Context reset 长跑 | ✅ Ralph 外层新会话 + HANDOFF 模板 | **有效**，且是非 Claude 模型更需要的路径 |
| 会话内自动续跑 / 目标锁定 | ✅ checkpoint + idle synthetic | **部分有效**；仍是“提示续跑”，不是 Claude 的深度 goal 状态机 |
| 多级 compaction / 工具结果预算 | ❌ 完全依赖 OpenCode 原生 | **无增量** |
| Dynamic workflow 脚本运行时 | ❌ 无等价实现 | **无增量**（OpenCode 侧也无 Claude 级 scripted workflow 运行时） |
| 模型内化的“坚持完成” | ❌ 无法复刻；只能靠提示 + 熔断 + 交接文件 | **有上限** |

**结论（第 2 点）**：  
UltraCode **有针对性地复刻了** Claude Code 在**工程方法论与外层编排**上最可移植的部分（子代理分工、独立评审、浏览器 QA、reset+handoff、开工前澄清），且与 Anthropic 公开的 long-running harness 论文方向一致，**理论上有效**。  

它**没有、也声明不追求**复刻 Claude Code 的完整 harness 内核与模型对齐优势。`docs/RESEARCH.md` 也写明：不宣称配置后即可达到 Claude Code + Claude 的等效能力。

## 3. “大量派子代理 + 8–9 小时明确目标坚持做完”——UltraCode 能否理论上同等实现？

用户描述的 Claude Code 独有观感，可拆成三层：

### A. 倾向多派子代理  
- UltraCode **在提示与角色设计上鼓励** 探索/实现/评审拆到独立 subagent。  
- 实际是否“很多”仍取决于**当前模型**是否遵守 system/角色指令（Claude 权重更对齐，廉价模型常更保守或更乱）。  
- OpenCode 后台 subagent（V2.3+）提供了机制基础；UltraCode 没有再实现更高层的 fan-out 调度器。

### B. 上下文明确、问题事先定死之后的端到端实现力  
- 这与 Claude Code 的 **clarification + 验收标准 + 证据型完成判定** 一致。  
- UltraCode 用 orchestrator 强制批量选择题 + Sprint Contract 类模板，**方向正确**。  
- 落地质量仍强依赖模型：同一 harness 下 Claude vs 中小模型差距会缩小但不会消失。

### C. 8–9 小时级“自始至终完成”  
这里要区分两种工程路径：

| 路径 | Claude Code 常见做法 | UltraCode 理论能力 |
|------|----------------------|-------------------|
| 单会话硬撑极长上下文 | 强 compaction + 模型低 anxiety | **较弱**：无额外 compaction 引擎；靠 OpenCode 原生压缩 + checkpoint 续跑，长会话仍可能腐烂 |
| 外层重置 + 磁盘状态机 | 官方/社区 long-running harness、workflows | **设计主战场**：Ralph 新会话 + HANDOFF/PROGRESS + 熔断，正是 Anthropic 推荐给非顶级对齐模型的路径 |

因此：

- **若坚持“一个会话窗口里连续 8–9 小时不丢目标”**：UltraCode **不能**在理论上宣称与 Claude Code 同等；缺模型对齐与 harness 深度。  
- **若接受“多轮新会话 + 仓库内 handoff/任务清单/Git 证据续跑，总墙钟时间 8–9 小时”**：UltraCode **在架构上可以逼近** 同一类交付结果，尤其在无限额度廉价模型场景下，**reset 比硬撑更合理**。  
- **“会倾向于更多派遣子代理”**：有制度设计，**无硬保证**；需模型配合与用户明确目标。  
- 项目自身 RESEARCH 的诚实边界与此一致：不宣称纯血 Claude Code 等效。

---

## 总评（是否“充分复刻了 Claude Code 第一性本质架构”）

**没有充分复刻 Claude Code 的完整 agentic harness 内核。**  
它做的是：**在 OpenCode 上叠加一套与 Anthropic 公开 long-running 方法论同构的 Goal Engineering 外壳**。

- **充分复刻的部分**：独立子代理、反自评、真浏览器验收、开工澄清、外层 context reset + 持久 handoff、长跑熔断与控制面。  
- **刻意未做 / 做不到的部分**：Claude 级 compaction 栈、dynamic workflow 脚本运行时、权限 ML 分类器、以及模型权重内的“坚持完成”对齐。  

相对 **原版 OpenCode**，亮点是真实的、可从源码验证的工程层增强。  
相对 **Claude Code 极长任务观感**，理论上限是 **“方法论级逼近（尤其 Ralph 多会话路径）”**，不是 **“单会话同等 harness + 同等模型行为”**。  

若你的目标是用 OpenCode + 任意模型尽量接近 Claude Code 的长程交付，UltraCode 是合理且比“只换模型不改编排”更接近第一性的一层；若目标是 1:1 复刻 Claude Code 的 agentic loop 与 harness 厚度，当前仓库**不是**那条路径。
