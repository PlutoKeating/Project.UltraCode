Project.UltraCode 深度架构审计
这次审计需要区分三个完全不同的层次：
1. 功能复刻：有没有实现 Claude Code / OpenCode 已有的功能，例如 Agent、Subagent、Plan、Tool、MCP、Hooks？
2. 架构复刻：有没有复刻这些功能背后的运行时机制、状态管理、调度机制、上下文管理和工程执行闭环？
3. 能力复刻：在面对一个预先定义清楚、规模很大、持续执行 8～9 小时的复杂工程任务时，能否持续分解、派遣子代理、并行实现、集成、测试、修复，最终真正交付完整成果？
第三层才是这次审计最重要的判断标准。

我不会把 README 中出现了某项功能，直接视为具备了相应的工程能力。尤其是 Subagent：能够创建子代理，不等于能够形成有效的多代理工程组织；能够压缩上下文，不等于能够跨上下文窗口持续完成任务；能够循环调用 LLM，也不等于具备可靠的 Agentic Engineering 能力。

我会以 UltraCode 的实际源码为主要证据，以 OpenCode 官方源码作为基线，并结合 Claude Code 的公开架构研究、Anthropic 官方工程文章，以及其他成熟 Agent Harness 的实践进行交叉验证。

一、先建立正确的评价基准
有一个非常重要的结论值得先明确：

Claude Code 的工程能力护城河，不是某一个 Agent Loop，也不是单纯依赖更强的模型，而是模型、Harness、上下文管理、工具执行、子代理组织、任务持久化和验证机制形成的整体系统。

Anthropic 在 2025 年 11 月发布的《Effective harnesses for long-running agents》中，已经明确展示了一个关键问题：即使使用能力很强的模型，并且拥有上下文压缩机制，也不意味着它能可靠地跨越多个上下文窗口完成大型工程任务。

他们为此引入了初始化代理、增量执行、进度文件、Git 历史以及每次执行后的干净状态维护机制。

Anthropic+1

这也是我判断 UltraCode 是否真正实现长期自主工程能力的核心依据之一。
二、UltraCode 相对于原版 OpenCode 的实际增量
首先明确一个架构事实：UltraCode 并没有重新实现 OpenCode 的底层 Agent Runtime，而是通过官方插件、Agent 配置、CLI 包装器和持久化工作流，在 OpenCode 之上构建一层 Goal Engineering。

这实际上是一个合理的技术路线。没有必要为了增加工程能力而重写成熟的模型调用、工具执行和会话管理系统。

但它也意味着：UltraCode 的能力上限，很大程度上取决于它是否真正有效地利用了 OpenCode 原生的执行机制，以及它自己增加的编排机制有没有补足原生 Runtime 的不足。

这里有五个值得特别肯定的设计。

第一，需求澄清前置化。

这是一个非常重要的改进。

传统 Agent 容易出现这样的情况：
- 需求还没有真正明确，就开始修改代码。
- 实现到一半才发现架构方向有问题。
- 用户纠正需求之后，之前的实现产生大量返工。
- 长时间执行后，原始目标被局部实现细节逐渐取代。
UltraCode 将重大产品和架构方向选择前置，通过结构化选项让用户确认。这在理论上可以显著降低目标歧义造成的返工。

第二，五个专业代理形成了初步的职责分工。
UltraCode Specialists
1. Librarian
   
   资料检索、官方文档、项目规范和既有实现调查。
2. Architect
   
   架构分析、模块边界、根因分析和设计权衡。
3. Implementer
   
   承担边界明确的代码实现和项目原生验证。
4. Reviewer
   
   独立审查代码变更、回归风险和需求遗漏。
5. Visual Evaluator
   
   真实 Chromium 浏览器中的交互、布局和视觉验收。

这比单纯配置一个通用 Subagent 更有工程意义：它尝试把软件开发中的不同认知任务分离出来。

不过，必须强调：五种角色的存在并不能证明已经实现了有效的多代理协同。真正决定效果的是主代理如何选择角色、如何分配任务、如何处理代理之间的冲突，以及如何整合和验证结果。

第三，Ralph 外层迭代机制。

这是我认为 UltraCode 最值得重视的增量之一。

它明确区分了两种隔离：
- Subagent：在同一工程任务中，使用独立的上下文执行局部任务。
- Ralph：在外层迭代中创建全新的会话，以新的上下文继续整个目标。
这两者不能相互替代。

Ralph 的价值在于，避免一个 Agent 在同一个不断膨胀的上下文中持续工作，最终受到上下文污染、历史信息压缩和目标漂移的影响。

第四，持久化 Milestone 和 Handoff。

UltraCode 不只是依赖聊天记录延续任务，而是将进度、已验证证据和下一步计划放到仓库中。

其架构还引入了：
- BOOT_ID 启动围栏，防止旧进程状态在重启后错误触发。
- MAX_CHECKPOINT_ROUNDS = 25，限制单轮自动推进次数。
- MAX_CHECKPOINT_STALLS = 3，阻止无效推进无限循环。
- 官方 /goal 共存检测，避免两个续跑机制互相争夺控制权。
这已经超出了简单的 Prompt Engineering，进入了工作流状态管理和运行时控制的范畴。

GitHub+1

第五，真实浏览器验收。

这一点非常重要。

传统代码 Agent 很容易将以下情况误认为任务完成：
- 编译成功。
- TypeScript 类型检查通过。
- 单元测试通过。
- 页面可以启动。
但这并不能证明实际产品能够正常工作。

Visual Evaluator 将浏览器交互、桌面与移动端视口检查，以及发现问题后的修复复验纳入流程。这使得它具备了一种更接近真实工程师的验证方式。

UltraCode+1


三、与 OpenCode 官方最新架构的对照：真正关键的 Agentic Loop
这一部分必须深入，因为 UltraCode 的绝大部分实际工程能力最终还是由 OpenCode Runtime 执行。

我将官方 OpenCode V2 的 Agent 和 Compaction 文档作为当前行为基线，同时参考官方仓库，而不是将旧版本 OpenCode 的架构直接套用到 V2。
3.1 OpenCode 原生已经具备什么？
首先要纠正一个可能产生误判的地方：OpenCode 本身并不是一个简单的单 Agent 聊天工具。

它已经具备：
- Build / Plan 主代理。
- General / Explore 子代理。
- 独立子会话上下文。
- 子代理后台执行和结果回传。
- Agent 级别权限控制。
- 工具调用和执行结果循环。
- 自动上下文压缩。
- Session 持久化。
- MCP 和插件扩展机制。
官方 Agent 文档明确指出，Subagent 在独立子会话中运行，父代理可以收到其进入空闲状态时的报告，以及后续工作轮次的报告。

OpenCode+1

这意味着 UltraCode 的五个 Specialists，本质上是在原有能力上增加专业化的角色定义和工作组织方式。

它并没有从零发明多代理系统。
3.2 OpenCode 的上下文管理并不等于长期工程管理
OpenCode V2 的 Compaction 有一个值得注意的机制：
OpenCode V2 上下文压缩机制
压缩前

System Prompt + 历史对话 + 最近约 15,000 Tokens + 待执行任务

Automatic / Background Compaction

压缩后

历史摘要 + 最近约 15,000 Tokens + 待执行任务

示意图。默认保留约 15,000 Tokens 的近期对话，具体取决于配置。
它还支持后台预先生成摘要，以及为摘要指定独立模型。

OpenCode+1

但是，必须理解一个根本性问题：

上下文压缩解决的是信息窗口容量问题，而不是任务执行连续性问题。

例如：

一个 Agent 已经完成了 60% 的工程工作。

它压缩上下文之后，仍然可能：
- 忘记为什么选择某种架构。
- 丢失尚未完成的隐含依赖。
- 无法准确判断哪些功能已经真正验证。
- 误以为某个未完成的功能已经完成。
- 重新实现已经实现过的功能。
- 在后续任务中偏离原始验收标准。
所以，一个真正优秀的长期 Agent，必须有上下文管理之外的第二套机制：

持久化的工程事实、任务状态、验收条件和下一步执行计划。

UltraCode 已经在这个方向上做了相当有价值的工作。
3.3 Claude Code 的真正架构护城河
这里我参考了 2026 年 4 月公开的 Claude Code 架构研究《Dive into Claude Code: The Design Space of Today's and Future AI Agent Systems》。

这项研究基于公开 TypeScript 源码进行分析，识别出五个特别重要的系统特征：
1. 七种权限模式与 ML 辅助权限分类。
2. 五层上下文压缩体系。
3. MCP、Plugins、Skills、Hooks 四类扩展机制。
4. 支持 Worktree 隔离的 Subagent 委派机制。
5. Append-oriented Session Storage。
研究还特别指出，真正复杂的不是那个调用模型、执行工具、重复循环的简单 While Loop，而是围绕这个 Loop 建立的系统。

arXiv

我将这些能力进一步归纳为八个工程维度：
工程维度	核心问题	高水平系统需要具备的能力
1. 目标理解	知道要做什么吗？	消除歧义、约束提取、目标保持
2. 任务规划	知道怎么完成吗？	分解、依赖图、动态重规划
3. 代理组织	知道谁来做吗？	子代理调度、并行、隔离
4. 上下文管理	能持续理解吗？	Compaction、记忆、状态恢复
5. 工具执行	能真正操作环境吗？	Shell、Git、浏览器、MCP
6. 质量验证	知道是否做对了吗？	独立 Review、测试、运行验证
7. 故障恢复	失败后怎么办？	重试、检查点、回滚、恢复
8. 长期自治	能持续完成目标吗？	持久化、进度推进、完成判定

这里还有一个非常值得关注的行业实践。

OpenAI 在 2026 年 2 月公开的 Harness Engineering 实践中，展示了 Codex 如何通过：
- 仓库内的知识体系。
- 版本化的执行计划。
- 多轮 Agent Review。
- Git Worktree 隔离。
- 真实浏览器验证。
- Logs、Metrics、Traces 等可观测性能力。
- 自动修复和持续验收。
实现单次持续六小时以上的工程任务。

尤其重要的是，他们发现单纯把所有规则堆进一个大型 AGENTS.md 并不好，应该通过渐进式知识披露、可验证的架构约束和自动化检查来保持系统的一致性。

OpenAI+1

这与 Anthropic 关于长期 Agent 的研究形成了很好的互补：
- Anthropic 强调跨上下文窗口的任务连续性。
- OpenAI 强调工程环境的 Agent 可读性、可验证性和结构约束。
两者实际上共同指向了同一个结论：

优秀的工程 Agent 必须把工程任务本身变成一个可观察、可恢复、可验证、可持续推进的系统，而不是仅仅让模型持续生成代码。

这里需要展开几个容易被低估的问题。
4.1 五个子代理还不等于真正的多代理工程调度系统
UltraCode 的角色设计是合理的，但真正优秀的 Multi-Agent Orchestration 至少需要回答以下问题：
- 什么情况下必须派遣子代理？
- 什么情况下不应该派遣？
- 哪些任务能够并行？
- 哪些任务存在严格的先后依赖？
- 子代理的输出如何被验证？
- 多个子代理修改相同文件时怎么办？
- 一个子代理失败，是否影响其他代理？
- 子代理的结果不一致时，谁负责裁决？
尤其是最后三个问题。

例如，Architect 和 Implementer 分别提出了不同的技术方案，Reviewer 又发现其中一个方案存在问题。

此时主代理必须具备真正的冲突处理和重新规划能力。

五种角色并不会自动产生这种能力。

我没有获得足够的源码级证据，证明 UltraCode 已经实现了完整的动态任务 DAG、冲突仲裁、依赖感知调度和失败后的任务重分配。

这是一个重要的能力缺口，而不只是实现细节。
4.2 Child Session 隔离与 Git Worktree 隔离是两回事
这是我特别想强调的一点。

OpenCode 的 Subagent 拥有独立上下文，但这并不意味着它拥有独立的代码工作区。
上下文隔离
Agent A

独立上下文

独立上下文


可能仍然共享同一份工作目录

真正的代码工作区隔离
Worktree A

独立分支、文件状态

Worktree B

独立分支、文件状态


可以独立修改、测试、提交，最终再集成

这对大型工程非常关键。

如果三个 Implementer 同时修改：
- auth/service.ts
- database/schema.ts
- api/controller.ts
那么即使它们的上下文完全隔离，也可能产生文件冲突、接口不一致和相互覆盖。

UltraCode 的 Ralph 外层机制确实使用 linked Git Worktree，但不能因此推导出每一个 Specialist 都有独立 Worktree。

这两种隔离需要分别设计。
4.3 Checkpoint 目前更像可靠的续跑机制，而不是完整的任务状态机
我认为 UltraCode 在这里做出了正确的第一步，但还没有充分证明已经解决了长期工程的核心难题。

例如，一个大型任务可能有：
- 12 个一级目标。
- 47 个二级功能。
- 130 个测试条件。
- 20 个跨模块依赖。
- 8 个尚未解决的技术风险。
仅仅记录当前 Milestone 和下一步计划是不够的。

还需要持久化：
1. 每项需求的唯一 ID。
2. 需求之间的依赖关系。
3. 每项任务的执行状态。
4. 实际修改的文件及提交。
5. 测试和验收证据。
6. 当前阻塞原因。
7. 重试次数及失败历史。
8. 后续任务的重新规划依据。
尤其需要区分：

implemented、tested、reviewed、accepted。

不能把 Agent 自己声称完成，直接作为工程完成的事实。
4.4 缺少充分证据的另一个重要能力：动态模型路由
UltraCode 的架构文档明确指出，各角色默认继承当前 OpenCode 会话模型。

GitHub

这意味着它并没有在架构上证明：
- Librarian 使用低成本、高检索能力模型。
- Architect 使用高推理能力模型。
- Implementer 根据任务难度选择模型。
- Reviewer 使用独立的强模型。
- Visual Evaluator 使用适合视觉任务的模型。
它提供了模型池查询和授权切换的能力，但这与自动化的分阶段模型路由不是一回事。

这会影响长期任务的经济性和能力上限。

例如，一个持续八小时的工程任务，如果所有子代理都继承同一个高成本模型，那么它可能浪费大量资源；如果全部继承较弱模型，又可能导致架构设计和最终审查质量下降。

这并不意味着模型路由是 Claude Code 独有的能力，而是成熟 Agent Harness 值得补足的工程能力。

五、最重要的问题：UltraCode 能否达到连续 8～9 小时自主工程开发的水平？
现在进入本次研究最重要的部分。

我先给出判断：
理论上具备实现基础，但尚不能认定同等实现
UltraCode 已经具备实现长时间任务连续执行的几个关键机制：
- 专业子代理
- 独立上下文
- 持久化进度
- 自动 Milestone 推进
- 全新会话续跑
- Git Worktree
- 浏览器验证
- 停滞熔断
但尚未充分证明它具备 Claude Code 所表现出来的那种持续数小时、主动扩大代理并行规模、动态修复、持续集成和最终严格完成全部需求的综合能力。

5.1 8～9 小时任务究竟需要什么？
假设你给 Agent 一个完整的工程任务：
从零构建一个包含用户系统、权限管理、数据库、API、管理后台、前端界面、自动化测试和部署能力的完整应用。所有功能必须完成，所有模块必须集成，最终通过测试。

你已经把需求、技术栈、架构原则、验收标准全部提前确定。

这个任务实际上需要一个持续运转的工程组织。

我认为它至少需要以下六个阶段：
理想的 8～9 小时 Agentic Engineering 工作流
1. 阶段 1：需求与工程环境初始化
   
   理解完整 Spec、建立工程结构、识别依赖、生成验收条件、建立 Git 基线。
   UltraCode 已有对应机制
2. 阶段 2：架构设计与任务 DAG
   
   Architect 分析架构，拆解成可独立执行的任务，建立依赖关系和并行边界。
   部分覆盖
3. 阶段 3：多代理并行实施
   
   派遣多个 Implementer，分别负责数据库、后端、前端、测试等模块。
   部分覆盖
4. 阶段 4：集成、Review 与修复
   
   独立审查、接口对齐、冲突解决、自动测试、失败任务重新派遣。
   部分覆盖
5. 阶段 5：端到端验收
   
   启动完整系统，执行用户工作流、浏览器验证、边界测试和回归测试。
   已有较好基础
6. 阶段 6：最终交付与完整性确认
   
   逐项核对 Spec、测试证据、未完成事项、技术债务和最终交付状态。
   部分覆盖

5.2 真正决定 8 小时任务成败的，是三个循环
我认为这三个循环比单纯增加 Subagent 数量重要得多。

循环 A：任务推进循环
读取工程目标
    ↓
识别尚未完成的任务
    ↓
分析依赖与优先级
    ↓
选择可并行任务
    ↓
派遣专业代理
    ↓
收集执行结果
    ↓
更新任务状态
    ↓
继续下一批任务


循环 B：质量保障循环
实现功能
    ↓
运行测试
    ↓
独立 Review
    ↓
发现问题？
  ↙       ↘
 是         否
 ↓          ↓
修复      验收通过
 ↓          ↓
重新测试   标记完成


循环 C：上下文续航循环
当前会话执行
    ↓
上下文接近容量限制
    ↓
保存工程状态
    ↓
记录决策、证据和下一步
    ↓
安全结束当前会话
    ↓
启动全新会话
    ↓
重新读取工程状态
    ↓
核验实际代码和任务状态
    ↓
恢复执行


UltraCode 在循环 C 上已经有比较明确的设计。

它的 Ralph + Checkpoint + Handoff 机制是有意义的。

但 A 和 B 还需要更强的机制保证。

尤其是：

如果 Agent 在连续执行 8 小时之后，完成了 90% 的工作，却错误地宣布任务结束，那么它的长期执行能力实际上并不合格。

所以最终完成条件必须由外部可检查的工程事实决定，而不能由模型自身的主观判断决定。
5.3 为什么 Claude Code 会表现出你描述的那种特别强的自主工程能力？
这里有一个非常关键的认识：

Claude Code 的优势不只是倾向于多派遣代理，而是它能够把代理调用作为整个工程执行策略的一部分。

例如：
- 复杂问题交给多个代理独立研究。
- 需要大量代码修改时，分解不同实现职责。
- 需要验证时，另外派遣代理审查。
- 出现问题时，主动重新调查根因。
- 发现原有计划不合理时，重新规划。
- 主上下文接近容量限制时，利用上下文管理机制延续工作。
这是一种动态工程组织能力。

UltraCode 当前的五个角色属于预设专业分工，但我没有足够证据证明它已经实现了同等成熟的动态代理组织策略。

此外，还有一个很容易被忽略的因素：

真正强的 Agent 不会仅仅因为某个子任务完成，就认为整个项目已经完成。

它需要持续检查全局目标与局部实现之间的差距。

Anthropic 的长期 Agent 研究特别指出，Agent 会在后续会话中看到已有进展，就过早判断任务已经完成。因此他们专门设计了增量执行和明确的跨会话进度记录机制。

Anthropic+1

UltraCode 的方向是正确的，但还需要把这种机制进一步工程化。

六、UltraCode 目前最值得补强的架构
如果我的目标是让 UltraCode 真正达到你描述的 Claude Code 工程效果，我不会建议推倒重来。

我会保留目前的 OpenCode Runtime、五种 Specialists、插件控制面、Ralph 和跨平台安装体系。

真正应该升级的是它的工程编排层。

这是我认为最优先的升级。

目前的 Milestone 不应该只是一个下一步任务描述，而应该升级为完整的、可恢复的工程任务图。

pending → ready → running → implemented → tested → reviewed → accepted

失败则进入 blocked 或 failed，而不是直接被主代理标记为完成。
6.2 建立真正的 Multi-Agent Orchestrator
我建议将现有 UltraBuild 升级为具备明确调度职责的 Orchestrator。

它不应该只是一个拥有五个子代理的主 Agent，而应该负责：
- 维护全局任务 DAG。
- 动态选择子代理。
- 判断并行执行条件。
- 分配独立 Worktree。
- 管理任务依赖。
- 收集子代理产物。
- 处理冲突。
- 触发 Review。
- 根据测试失败重新派遣任务。
- 维护整体工程进度。
这里特别建议引入一个概念：

Agent Worker 不拥有整个项目的最终完成权。

Worker 只负责自己的任务和验收证据；Orchestrator 负责全局状态与最终完成判定。

这可以显著降低模型自我评价过于宽松的问题。
6.3 每个实施代理应该有独立 Worktree
我建议将现有的 Ralph Worktree 机制扩展到 Specialist 的实际工程执行中。

例如：
Agent	工作区	任务
Implementer A	worktree/backend	后端
Implementer B	worktree/frontend	前端
Implementer C	worktree/database	数据库
Reviewer	Read-only	审查
Integrator	Main Integration	集成

集成阶段再统一处理：
- 接口一致性。
- 数据结构兼容性。
- 合并冲突。
- 回归测试。
- 完整系统运行。
这能让并行代理的收益真正转化为工程吞吐量，而不只是增加模型调用次数。
6.4 引入 Evidence-Based Completion
最终完成判定不能依赖模型说：
All tasks are completed successfully.

而应该检查：
- 原始 Spec 是否完整映射到任务图。
- 所有必要任务是否达到 Accepted。
- 必需测试是否通过。
- 是否存在未解决的 Blocker。
- 是否存在未合并的 Worktree。
- 最终集成构建是否通过。
- 是否存在未经验证的功能声明。
甚至可以引入一个独立的 Final Auditor，它不负责实现，只负责根据原始 Spec 和实际工程证据判断是否允许交付。

这比单纯增加一个 Reviewer 更重要。
6.5 建立长期执行的资源和故障管理
八小时任务还涉及现实世界的工程问题：
- 模型请求超时。
- API 限流。
- 子代理失联。
- 工具执行失败。
- 进程意外退出。
- 磁盘空间不足。
- Git 冲突。
- 依赖安装失败。
- 预算耗尽。
所以还需要：
1. 任务级超时与重试策略。
2. 子代理租约和心跳。
3. 幂等任务执行。
4. 持久化事件日志。
5. 失败任务恢复。
6. 成本与 Token 预算管理。
7. 并行度限制。
8. 人工介入和安全停止机制。
这些能力不需要全部自己发明，但必须确保各机制能够形成完整闭环。

七、最终审计结论
我把目前的研究结果归纳成三个问题，直接回答你最初提出的要求。
问题一：相对于原版 OpenCode，UltraCode 最显著的亮点是什么？
我认为有六项真正值得肯定的增量。
排名	增量	我的评价
1	Ralph + Checkpoint + Handoff	非常有价值
2	UltraBuild + 专业 Specialists	非常有价值
3	前置需求澄清	非常有价值
4	Reviewer + Visual Evaluator	非常有价值
5	实时多端控制面	产品化程度高
6	上游兼容性看护体系	工程维护价值高

尤其是 Ralph、Checkpoint 和 Handoff 的组合。

这实际上是在 OpenCode 原有的单会话执行能力之上，增加一层跨会话的长期目标执行机制。

我认为这是 UltraCode 最有价值的架构方向。
问题二：是否充分复刻了 Claude Code 的核心工程能力？
我的判断是：

已经复刻了部分重要的架构思想，但还没有充分证明复刻了 Claude Code 的完整工程能力。

目前最明显的不足是：
1. 没有充分证明已经具备动态任务 DAG 和依赖调度。
2. 没有充分证明多代理具备成熟的冲突仲裁和任务重分配能力。
3. 子代理上下文隔离不等于代码工作区隔离。
4. 持久化 Checkpoint 不等于完整的工程事实数据库。
5. Ralph 续跑不等于具备可靠的跨会话任务完成判定。
6. 尚未证明具有充分的分阶段模型路由和资源管理能力。
7. 缺乏足够证据证明具备持续性的架构约束、全局质量控制和最终独立验收机制。
问题三：能否达到 Claude Code 那种 8～9 小时的工程能力？
目前不能认定同等水平
但这不是说 UltraCode 做不到。

恰恰相反，我认为它已经有了相当好的基础。

我会把它目前的能力理解为：
- 有较好的任务连续性设计。
- 有明确的专业代理体系。
- 有独立会话续航机制。
- 有实际浏览器验收机制。
- 有工程进度持久化意识。
但是，距离一个真正能够长时间自主组织工程团队、主动扩展代理规模、持续解决集成问题并严格交付全部需求的系统，还缺少一个关键层：

真正意义上的 Engineering Orchestration Runtime。
